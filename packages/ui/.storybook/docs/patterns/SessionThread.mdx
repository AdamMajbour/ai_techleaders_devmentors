# Session thread

## 1. What it is for

A short written conversation between a seeker and a mentor, inside a time window. The conversation is the centre of the page (R02.1); the window is stated in words and enforced by the server.

<Canvas of={SessionPatternStories.WindowStatedInWords} />

## 2. When to use it

- The session of an accepted booking (E01-S04).

## 3. When not to use it, and what to use instead

| Situation | Use instead | Why |
|---|---|---|
| A chat without a time window | Not in the product | Sessions are limited by time |
| A finished answer | `MarkdownView` in a Detail view | It is a document, not a conversation |

## 4. Anatomy

1. **Page title**: the session with the other person.
2. **Window line**: where the session stands, in words.
3. **Messages**: author, time, text, code as code.
4. **Message box**: blocked outside the window, with the reason.

## 5. Behavior rules

| Rule | Why | Source |
|---|---|---|
| **One column**, the conversation in the centre, no sidebar | The session has one task | R02.1. The "no sidebar" part is proposal P5 (R02.6), not approved |
| **Roomy** spacing in the session, dense in lists | K1 | K1 (approved 2026-10-27) |
| **Author and time** with every message | The mentor sees who asks, the messages are the record | R02.3 |
| The message box is **always in reach** and sends with Ctrl or Cmd plus Enter | Writing and answering is quick | R02.2 (form of the box: proposal) |
| The window is stated **in words, not as a ticking countdown** | A countdown is announced every second | WCAG 4.1.3, Proposal |
| The **server decides the window**: the page shows the time of the last answer | The browser's clock may be wrong | Booking spec (clock skew) |
| **New messages are announced politely**, nothing is re-read | A screen reader user keeps the context | WAI-ARIA `aria-live="polite"`, Booking spec |
| **After the end the conversation stays readable**; only the box is blocked, with the reason | The conversation is the result of the product | Proposal |
| When **refreshing fails, the messages stay** and an alert says so | What is shown is still correct | Proposal |
| **Only fenced code is formatted**, nothing else is rendered | Messages are user input | Booking spec (code in messages, approved default) |
| No notification counters in the thread | Quiet product | Proposal P4 (R02.4), not approved |

## 6. States, one story each

| State | Story |
|---|---|
| In the window, with the minutes left | WindowStatedInWords |
| Before the start: the box is blocked | BlockedBeforeTheWindow |
| After the end: read-only | ReadOnlyAfterTheWindow |
| Polling failed, the messages stay | RefreshFailsAndTheMessagesStay |
| Loading | Loading |
| The conversation could not be loaded | LoadFails |

## 7. Accessibility

- The thread is a `section` named "Session". Messages are an ordered list with `aria-live="polite"`.
- The window line is plain text, not a live region.
- The message box has a name, and when blocked it is described by its reason.
- Own messages carry the words "(you)".

## 8. Content

- **Window line:** "12 minutes left. The session ends at 13:25."
- **Blocked box:** "The session has not started yet. You can write when it starts."
- **Refresh failed:** "New messages could not be loaded. We keep trying. What you see so far is still correct."

## 9. Responsiveness

The column is at most `max-w-session` wide and stays centred. At 320 px it takes the full width. Code scrolls sideways inside its message.

## 10. Code

```tsx
<SessionThread
  messages={messages}
  viewerId={me.id}
  startsAt={startsAt}
  endsAt={endsAt}
  now={serverTime}
  status={status}
  refreshFailed={refreshFailed}
  onRetry={reload}
  onSend={send}
/>
```

## 11. Do and don't

| | Example | Why |
|---|---|---|
| Do | "12 minutes left. The session ends at 13:25." | A fact the reader can plan with |
| Don't | A countdown that ticks every second | Announced every second |
| Do | Keep the messages when the refresh fails | They are still correct |
| Don't | Replace the thread with an error | The user loses the conversation |
