# What is missing

Priority is the author's proposal, taken from the order of the backlog (dependencies) and from what blocks the pilot.

## States and behaviours that are missing

Workarounds approved by the owner on 2026-10-28. Source: the agent test of that day (screen "My sessions").

| Missing | Until then | Where it shows |
|---|---|---|
| **Refresh failed after the list loaded.** `SessionThread` has `refreshFailed`, a list has nothing | Keep the last result and put an `Alert` above the list: "The list could not be refreshed. It shows the last result." with a "Try again" button | Lists that poll or reload |
| **Error while a filter is active** | The error replaces the filter and the list. The filter value is kept and comes back after "Try again" | List with filters |
| **A next step per booking status.** `BookingRow` has only `href`, so `payment_failed` and `pending_payment` have no "pay again" | One "Open" link for every status. A "pay again" action waits for a spec of payment retry | Seeker's list |
| **The date of an accepted session in the row.** Decided to show it ("3 Nov 2026, 14:25", `formatDate` and `formatClock`), but `BookingRowData` has no `startsAt` | Leave it out of the row until `startsAt` is in the data | Seeker's list |
| **Session time stage** (upcoming, in progress, ended). A status filter cannot tell them apart: `accepted` covers all three | No filter by time stage | Seeker's list |
| **Filter kept in the address** (a link to a filtered list). `List with filters` points here | The filter is local state and is lost on reload | List with filters |
| **A list of rows for phones instead of a table that scrolls sideways.** `List with filters` and `DataTable` point here | A `ul` of rows (`MentorRow`, `BookingRow`) wraps by itself, a `DataTable` scrolls | Lists |

## Decided on 2026-10-28 (owner, agent test)

| Decision | Consequence |
|---|---|
| The seeker's list is called **"My sessions"**. Every booking, whatever its status, is a session for its seeker | Words in Content, "Words" section. E01 screens updated |
| The status filter lists **all six booking statuses**, in the seeker's wording | `bookingStatusLabel(status, 'seeker')` is the one source of the words |
| The row shows **date and time for an accepted session** | Needs `startsAt` in the data, see above |
| **"Specialization" is the mentor's `headline`.** There is no separate field | A seniority label alone is not a headline (A05) |
| The seeker's list is a `ul` of rows, not a `Table` (R01.3 for the **mentors** list stays open, below) | `List with filters`, `DataTable` and `How to choose` say so |
| The filter bar is shown only when the list has items; the filter field is `max-w-session`; the skeleton of a row is three lines (`h-6 w-1/3`, `h-4 w-2/3`, `h-4 w-1/3`), scale values without tokens | `List with filters` §5. The pattern story follows it |
| A list is in the order the server sends, newest first, with no sortable columns in the pilot. The status filter follows the order of the status type, "All statuses" first | `List with filters` §5 |
| The seeker's list lives at `/bookings` (booking spec) and is labelled "My sessions" | `/sessions` of the standards (S08) is not used |
| `GET /api/bookings` carries the mentor's `name`, `headline` and `technologies`, and `startsAt` for an accepted booking | Written into the booking spec (API table) |
