# What is missing

What is ready, what is not, and how the backlog is covered. "Ready" means built, tested in jsdom and documented. **Nothing here has been seen in a browser**, and no route of the product is built: every screen is an example with example data.

Priority is the author's proposal, taken from the order of the backlog (dependencies) and from what blocks the pilot.

## Components that do not exist

| Missing | Used for | Until then | Source |
|---|---|---|---|
| Action menu | Three or more actions for one row | Two actions per row | How to choose |
| Radio group | Two or three visible options | `Select` | How to choose |
| Search field (combobox) | A long list | A filter with `Select` | Booking spec: the list is a handful of mentors |
| Switch | A setting that applies at once | None needed in the backlog | How to choose |
| Side panel, popover, tooltip | Detail beside a list, small explanations | A page, text on the page | How to choose |
| Tabs | Views of the same record | Separate pages | How to choose |
| Toast | Short confirmations | Plain status text. An error is never a toast | WCAG 2.2.1 |
| Shared pagination control outside `DataTable` | A `ul` list with many rows | The caller provides pagination and passes at most 25 rows per page; do not render an unpaginated list that can exceed 25 rows | Owner decision 2026-10-31 |
| Action slot of `Alert` (a button beside or under the message) | Refresh failed after a list loaded | A `Button` as a child of the `Alert` | Agent test 2026-10-28, round 2 |
| A runtime list of the booking statuses. `BookingStatusValue` is only a type, so a filter repeats the list | The status filter | Repeat the six values in the order of the type | Agent test 2026-10-28, round 2 |
| The E01 mentors list does not yet follow **List with filters**: no count, no chip, no "Clear all filters" | The mentors list | It keeps the plain `Select` | Agent test 2026-10-28, round 2 |
| Success tone of `StatusBadge`, and a warning colour | Statuses | Three tones. `--status-success` exists as a token but no component uses it yet except the starter page | K3 settled for the colour on 2026-10-28; the component is not changed |
`FilterBar`, `Page` and `SessionRow` are built and are not missing components. Use `FilterBar` for the filter/chip/count order and filter behaviour in Patterns > List with filters; use `Page` for the page landmark and heading; use `SessionRow` for the seeker's session row, including its responsive layout and accepted-session date. Their component and screen stories are the examples of their anatomy.

## States and behaviours that are missing

Workarounds approved by the owner on 2026-10-28. Source: the agent test of that day (screen "My sessions").

| Missing | Until then | Where it shows |
|---|---|---|
| **Refresh failed after the list loaded.** `SessionThread` has `refreshFailed`, a list has nothing | Keep the last result and put a `destructive` `Alert` directly above the list, below the filter bar and the count: "The list could not be refreshed. It shows the last result." The "Try again" button (`variant="outline"`, `size="sm"`, `className="w-fit"`, because `Alert` stacks its children in a column) is a child of the `Alert`, because `Alert` has no action slot | Lists that poll or reload |
| **Error while a filter is active** | The error replaces the filter and the list. The filter value is kept and comes back after "Try again" | List with filters |
| **A next step per booking status.** `BookingRow` has only `href`, so `payment_failed` and `pending_payment` have no "pay again" | One "Open" link for every status. A "pay again" action waits for a spec of payment retry | Seeker's list |
| **The date of an accepted session in the row.** Decided to show it ("3 Nov 2026, 14:25", `formatDate` and `formatClock`), but `BookingRowData`, the type of `BookingRow`, has no `startsAt` | A screen with its own row type shows the date from `startsAt` (the API carries it). `BookingRow` gets the prop together with the row component | Seeker's list |
| **Session time stage** (upcoming, in progress, ended). A status filter cannot tell them apart: `accepted` covers all three | No filter by time stage | Seeker's list |
| **Retry in progress.** `ErrorMessage` has no "retrying" state | The page swaps the error for the loading state; in an `Alert` the button is disabled and reads "Trying again…" | Lists |
| **A private list that answers 401** (session expired) | `ErrorMessage` without retry ("Your session has expired. Sign in again.") and a `TextLink` "Sign in" | Seeker's list |
| **Filter kept in the address** (a link to a filtered list). `List with filters` points here | The filter is local state and is lost on reload | List with filters |
| **A list of rows for phones instead of a table that scrolls sideways.** `List with filters` and `DataTable` point here | A `ul` of rows (`MentorRow`, `BookingRow`) wraps by itself, a `DataTable` scrolls | Lists |
| **Production page and data integration for "My sessions".** The UI screen is a prop-driven example and its story uses sample data. The booking spec describes `/bookings` and `GET /api/bookings?role=seeker`, but those app routes are not built. The row's `href` and the empty state's `#mentors` target are example links, not production destinations; the destination for opening an individual session is not specified here | Keep data and `timeZone` supplied by the caller; connect the real page to the booking API and pass real navigation targets only when the app route is implemented. Do not treat story/sample links as route decisions | Seeker's list; booking spec and app routing |
| **Initial source and update policy for the seeker's time zone.** The row accepts an IANA `timeZone`; the booking spec says to use the seeker's profile time zone, but the profile field and its initial value are not implemented | Pass an explicit time zone to the UI; do not guess a browser-derived or default zone. Decide how the profile value is collected and updated before implementing the app route | Seeker's list; booking spec |
| **Sort key and tie-breaker for newest-first order.** The list contract says the server sends rows newest first, but the booking data contract does not identify which timestamp defines "newest" or how equal timestamps are ordered | Preserve the order supplied by the server in the UI. Decide and document the timestamp and stable tie-breaker in the booking/API contract before implementing server ordering | Seeker's list; booking spec |

## Decided on 2026-10-31 (owner, favorites screen)

| Decision | Consequence |
|---|---|
| The screen title is **"Favorite mentors"** | Use this wording for the page heading |
| With no saved mentors, show **"No favorite mentors yet"**, "Browse mentors and save the ones you want to find again." and a **"Find mentors"** button | `Content` > "Empty states"; the containing app supplies the destination |

| The caller owns pagination and passes at most 25 rows per page | `List with filters` > "Behavior rules"; `FavoriteMentors` renders the provided page |

## Decided on 2026-10-28 (owner, agent test)

| Decision | Consequence |
|---|---|
| The seeker's list is called **"My sessions"**. Every booking, whatever its status, is a session for its seeker | Words in Content, "Words" section. E01 screens updated |
| The status filter lists **all six booking statuses**, in the seeker's wording | `bookingStatusLabel(status, 'seeker')` is the one source of the words |
| The row shows **date and time for an accepted session** | Needs `startsAt` in the data, see above |
| **"Specialization" is the mentor's `headline`.** There is no separate field | A seniority label alone is not a headline (A05) |
| The seeker's list is a `ul` of rows, not a `Table` (R01.3 for the **mentors** list stays open, below) | `List with filters`, `DataTable` and `How to choose` say so |
| The filter bar is shown only when the list has items; the filter field is `max-w-session`; the skeleton of a row is three lines (`h-6 w-1/3`, `h-4 w-2/3`, `h-4 w-1/3`), scale values without tokens | `List with filters` §5. The pattern story follows it |
| A list is in the order the server sends, newest first, with no sortable columns in the pilot. The status filter follows the order of the status type, "All statuses" first | `List with filters` §5 |
| The seeker's list lives at `/bookings` (booking spec) and is labelled "My sessions" | `/sessions` of the standards (S08) is not used |
| `GET /api/bookings` carries the mentor's `name`, `headline` and `technologies`, and `startsAt` for an accepted booking | Written into the booking spec (API table) |
| The price in a row is the price of the booking (`priceMinor`, `currency` from the API), not the mentor's current price | Written into the booking spec and into Content |
| The status filter runs in the client over the seeker's whole list: `GET /api/bookings?role=seeker` returns all of the seeker's bookings in one response in the pilot | Written into the booking spec. A list longer than 25 rows needs pagination first |
| Dates shown to a seeker use the `timeZone` of the seeker's profile (an IANA name) | Written into the booking spec. **The spec has no seeker profile yet**, so the field must be added |
| Which production URL opens a session from the "Open" link | No detail route is specified by the booking spec; the story's example link is not a route decision | App routing |
| `refundStatus` has four values (`none`, `pending_approval`, `processing`, `refunded`), the same as `RefundState` | The booking spec said three. It now says four |
